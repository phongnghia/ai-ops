AI-Ops Landscape — Thị trường đang làm gì?

Bối cảnh · Industry
AIOps (Artificial Intelligence for IT Operations) — thuật ngữ do Gartner đặt ra năm 2017. Không phải "AI + Ops" mà là dùng AI/ML để tự động hóa và nâng cao IT operations: giám sát, phát hiện bất thường, tương quan sự kiện, tự động phục hồi. Năm 2024, thị trường AIOps toàn cầu đạt ~$3.5B và dự báo tăng 3x vào 2029.

Observability + AI

Dynatrace Davis AI

Causal AI — tự động tương quan hàng nghìn events để tìm root cause. Không cần manual correlation. Đã được dùng tại BMW, Vodafone.

Datadog Watchdog + AI Assistant

Tự động phát hiện anomaly trên metrics/logs/traces. AI Assistant (GPT-4) cho phép query bằng ngôn ngữ tự nhiên: "Tại sao p99 latency tăng?"

New Relic AI

NRQL AI — tự động suggest query. Anomaly detection + alert correlation. Giao diện chat để debug incident.

Incident Management + AI

PagerDuty AIOps

Alert noise reduction — filter 90% redundant alerts. Auto-triage incidents. "Intelligent alert grouping" gom nhiều alerts thành 1 incident.

OpsRamp AI Ops

Hybrid infrastructure monitoring với AI-driven root cause analysis. Predict failures trước khi xảy ra dựa trên historical patterns.

BigPanda AIOps

Event correlation từ nhiều nguồn (Nagios, Zabbix, CloudWatch). ML model tự học topology để phân loại incident.

CI/CD + AI

GitHub Copilot for CLI

gh copilot explain giải thích lỗi terminal. gh copilot suggest đề xuất lệnh fix. Tích hợp trực tiếp vào workflow của developer.

Harness AI / AIDA

Phân tích pipeline failure trong Harness CI/CD. Tự động suggest remediation. AIDA (AI Development Assistant) review PR và propose fixes.

Coralogix AI + Loggly

Log anomaly detection với ML. "Loggly Insight" tự phân loại patterns. Coralogix dùng Streama™ ML để phát hiện log outliers realtime.

Khi Jenkins Build Fail lúc 2 giờ sáng

Vấn đề thực tế
Hãy tưởng tượng: 2 giờ sáng ngày trước release. Jenkins báo đỏ. Bạn làm gì?
  • Mở Jenkins Console Output: thấy 3.000 dòng log. Lỗi thật nằm đâu đó ở giữa, giữa hàng trăm dòng INFO và WARNING không liên quan.
  • Tốn 15–30 phút: chỉ để tìm đúng dòng Exception hoặc BUILD FAILED, chưa kể thời gian phân tích nguyên nhân gốc.
  • Context Switching: copy-paste log sang Slack hỏi đồng nghiệp, mở IDE kiểm tra code, đọc docs dependency — mất thêm 30 phút nữa.
  • Security Risk: log thô chứa connection strings, tokens, credentials — nếu paste lên ChatGPT hay Slack, dữ liệu nhạy cảm bị lộ.
  • Lặp đi lặp lại: lỗi tương tự xuất hiện lần nữa sau 2 tuần — không ai nhớ giải pháp cũ, phải debug từ đầu.

04

LLM — Không phải Magic, Chỉ là Pattern Matching

Nền tảng AI · LLM
LLM (Large Language Model) là mô hình được train trên lượng text khổng lồ để dự đoán token tiếp theo. Nó không "hiểu" — nó nhận ra pattern. Nhưng vì nó đã đọc toàn bộ StackOverflow, GitHub issues, và docs, nó rất giỏi phân tích lỗi kỹ thuật.

Tại sao LLM phù hợp với bài toán log analysis?

Đã thấy lỗi này rồi: LLM được train trên hàng triệu GitHub issues, Stack Overflow, Maven/npm error reports. cannot find symbol hay NullPointerException — nó biết ngay nguyên nhân và cách sửa.

Natural Language Output: Thay vì bạn đọc stack trace, LLM dịch sang ngôn ngữ tự nhiên: "Lỗi do method calculateDiscount không tồn tại trong class, có thể bị đổi tên thành applyDiscount ở commit #f3a9..."

Flexible Context Window: LLM hiện đại có context window 128K–1M tokens — có thể đọc toàn bộ log file, test output, và stack trace trong một request duy nhất.

LLM không cần training thêm để phân tích log — chỉ cần Prompt Engineering tốt là đủ. Đây là điểm mạnh của approach này.

05

RAG — Bộ Nhớ Dài Hạn của AI

Nền tảng AI · RAG
RAG (Retrieval-Augmented Generation) = trước khi hỏi AI, tìm kiếm các tài liệu liên quan và nhét vào context của câu hỏi. AI không cần nhớ — chỉ cần đọc tài liệu được cung cấp và trả lời dựa trên đó. Giống như cho AI "tờ gian lận" trước khi vào thi.

Tại sao RAG quan trọng hơn Fine-tuning?

1

Không cần retrain model

Fine-tuning tốn GPU, thời gian, tiền bạc. RAG chỉ cần database và query — thêm dữ liệu mới ngay lập tức.

2

Context đặc thù của team

Lỗi OrderService xảy ra tháng trước, cách fix là gì — chỉ team bạn biết. RAG nhét kiến thức đó vào prompt.

3

Hai mode tìm kiếm

Keyword mode (default): extract error tokens → SQL LIKE query — nhanh, không cần GPU.
Vector mode: pgvector cosine similarity — tìm lỗi "tương tự ngữ nghĩa" dù không trùng từ khóa.

Trong demo này: Mỗi lần AI phân tích xong, kết quả được lưu vào PostgreSQL. Lần sau cùng lỗi xảy ra, RAG tìm thấy giải pháp cũ và AI có context tốt hơn.

Tiếp theo: LLM và RAG đã rõ — nhưng gọi thẳng OpenAI API có vấn đề gì? AI Gateway sinh ra để làm gì?

06

AI Gateway — Tại sao không gọi thẳng OpenAI?

Nền tảng AI · LiteLLM
AI Gateway (LiteLLM) là tầng proxy đứng giữa ứng dụng và các LLM provider. Backend chỉ cần gọi một endpoint OpenAI-compatible duy nhất — LiteLLM lo phần còn lại: chọn provider, fallback khi lỗi, timeout, retry, load balancing.

Vấn đề khi gọi thẳng API

  • Vendor lock-in: code dùng openai.ChatCompletion.create() — muốn chuyển sang Gemini phải viết lại toàn bộ.
  • No fallback: OpenAI rate-limit → cả hệ thống down. Không có cơ chế tự động chuyển sang provider khác.
  • API key management: mỗi service giữ key riêng → khó rotate, khó audit, dễ leak.
  • No local option: trong môi trường air-gapped hoặc data sensitive, không thể dùng cloud API.

LiteLLM giải quyết

  • OpenAI-compatible API: backend gọi /v1/chat/completions — giống OpenAI SDK nhưng có thể route bất kỳ đâu.
  • Automatic Fallback: Azure fail → Gemini → Ollama. Priority order cấu hình bằng model_list.
  • Centralized key management: chỉ LiteLLM giữ provider API keys. Backend chỉ biết master key nội bộ.
  • Hybrid routing: local Ollama cho dev/staging, cloud cho production — cùng một code.

Bước 1 — Jenkins Log Preprocessing

Code · Jenkins / Bash
Trước khi gửi log cho AI, phải lọc bỏ 95% nhiễu. 3.000 dòng log → 30 dòng lỗi thực sự → tiết kiệm token, tăng chất lượng phân tích. Đây là bước quan trọng nhất nhưng thường bị bỏ qua.

Jenkinsfile — post failure block

jenkins/Jenkinsfile 
post {
  failure {
    script {
      try {
        ansiColor('xterm') {
          sh '''#!/usr/bin/env bash
          set -euo pipefail
          readonly SCRIPTS_DIR="${LOCAL_WORKSPACE}/jenkins/scripts"
          # 1. Preprocess log → cleaned_log
          # 2. POST to backend → AI analysis
          # 3. Print formatted result
          source "${SCRIPTS_DIR}/analyze.sh"
          python3 "${SCRIPTS_DIR}/notify.py"
          '''
        }
      } catch (Exception error) {
        // Never let AI ops block the build result
        echo "AI Ops skipped: ${error.getMessage()}"
      }
    }
  }
}

Design decision: AI analysis nằm trong try/catch — nếu backend down hoặc LLM timeout, build result không bị ảnh hưởng. AI là enhancement, không phải điều kiện.

preprocess_log.sh + preprocess.py

preprocess_log.sh — log source resolution 
# Ưu tiên đọc log theo thứ tự:
# 1. JENKINS_LOG_FILE (disk — fastest, no auth)
# 2. LOG_FILE argument
# 3. BUILD_URL REST API + basic auth
# 4. Fallback placeholder

read_log_tail() {
  if [[ -n "${JENKINS_LOG_FILE:-}" ]]; then
    tail -n 100 "${JENKINS_LOG_FILE}"
    return
  fi
  # ... fallback to REST API ...
}
# Pipe qua preprocess.py
read_log_tail | python3 "${PREPROCESS_PY}"

preprocess.py — filter logic

Lấy 100 dòng cuối → filter các dòng chứa ERROR, FATAL, Exception, Failed → output ra stdout. Kết quả là cleaned_log chỉ còn ~20–50 dòng signal thực sự.

3.000 dòng × 4 token/dòng = 12.000 tokens. Sau filter: 30 dòng × 15 token = 450 tokens. Tiết kiệm 96% chi phí token.

GitHub Copilot for CLI làm điều tương tự khi bạn chạy gh copilot explain "$(cat error.log)" — nhưng chỉ hoạt động locally, không tích hợp được vào automated pipeline như cách này.

Tiếp theo: cleaned_log đã sẵn sàng → analyze.sh gọi POST /api/analyze-log → FastAPI backend nhận và bắt đầu orchestration.

Bước 2 — FastAPI Backend Orchestration

Code · Python / FastAPI

analyze.py — HTTP boundary (chỉ làm HTTP)

backend/app/api/analyze.py 
@router.post("/analyze-log",
             response_class=PlainTextResponse)
def analyze_log(
    request: AnalyzeLogRequest,
    service: Annotated[AnalysisService, Depends(...)],
) -> PlainTextResponse:
    request_id = str(uuid.uuid4())

    # Route layer chỉ: validate → log → delegate
    result = service.analyze(
        build_number=request.build_number,
        cleaned_log=request.cleaned_log,
        request_id=request_id,
        job_name=request.job_name,
        build_url=request.build_url,
    )
    return PlainTextResponse(
        content=result.text,
        headers={
            "X-AI-Provider": result.provider,
            "X-AI-Model":    result.model,
        },
    )

Layered Architecture: Route layer không có business logic. Tất cả logic nằm trong AnalysisService — testable độc lập, không cần HTTP context.

analysis_service.py — orchestrator

backend/app/core/analysis_service.py 
def analyze(self, build_number, cleaned_log,
             request_id, job_name, build_url):

  # Step 1: RAG — tìm lỗi tương tự từ quá khứ
  rag_context = self._retrieve_context(
      build_number, cleaned_log, request_id
  )
  # Step 2: Build prompt với RAG context
  messages = prompt_builder.build(
      cleaned_log, build_number, rag_context
  )
  # Step 3: Gọi LLM qua gateway
  result = self._complete(messages, ...)

  # Step 4: Lưu vào DB (best-effort — không block)
  self._save_best_effort(build_number, cleaned_log, ...)

  # Step 5: Gửi Slack/Teams notification
  self._notify_best_effort(build_number, ...)

  return AnalysisResult(text=result.text, ...)

Graceful Degradation Pattern

_save_best_effort và _notify_best_effort: fail không ném exception ra ngoài — log ERROR và tiếp tục. Caller luôn nhận được kết quả dù DB hoặc Slack bị down.

Tiếp theo: Prompt được xây dựng như thế nào? Đây là nơi "kỹ thuật" gặp "nghệ thuật" — Prompt Engineering.

Bước 3 — Prompt Engineering & RAG Assembly

Code · Prompt Engineering
Prompt là giao diện giữa bạn và LLM. Prompt tệ → output rác. Prompt tốt → output có thể parse và dùng ngay. Hệ thống này dùng structured output với 3 section cố định để downstream (Jenkins console, Slack) parse dễ dàng.

prompts.py — System Prompt

backend/app/core/prompts.py 
# Section labels — parsed by notify.py
SECTION_PROBLEM    = "🚨 Problem"
SECTION_ROOT_CAUSE = "🔍 Root Cause"
SECTION_FIX_STEPS  = "🛠️ Fix Steps"

SYSTEM_PROMPT = (
  "You are a CI/CD failure analysis expert..."
  "Always respond in English using plain text only"
  "— no # headings, no ** bold markers."
  "Use exactly these three section labels:"
  "\n\n🚨 Problem\n"
  "A concise 1-3 sentence summary.\n\n"
  "🔍 Root Cause\n"
  "The underlying cause...\n\n"
  "🛠️ Fix Steps\n"
  "Specific, actionable steps..."

Tại sao Plain Text, không phải Markdown?

## Heading và **bold** render đẹp trong web nhưng hiển thị ký tự thô trong Slack (*bold* là Slack format) và Teams. Plain text + emoji labels → universal format cho mọi channel.

prompt_builder.py — Assembler

backend/app/core/prompt_builder.py 
def build(cleaned_log, build_number, rag_context):
  user_parts = [
      f"Build: {build_number}",
      f"Log:\n{cleaned_log}",
  ]
  if rag_context:
      user_parts.insert(0,
          "Similar past failures for context:\n"
          + rag_context
      )
  return [
      {"role": "system",
       "content": SYSTEM_PROMPT},
      {"role": "user",
       "content": "\n\n".join(user_parts)},
  ]

Assembled Prompt Structure

System: SYSTEM_PROMPT (role + output format instructions)

User [optional]: RAG Context từ DB (past similar failures)

User: Build number + cleaned_log (current failure)

class LiteLLMClient:
  def complete(self, messages) -> LLMResult:
    response = self._http.post(
        f"{self._gateway_url}/chat/completions",
        json={
            "model":    "log-analyzer",
            "messages": messages,
        },
        headers={
            "Authorization":
                f"Bearer {self._api_key}"
        },
        timeout=self._timeout,
    )
    choice = response.json()["choices"][0]
    return LLMResult(
        text     = choice["message"]["content"],
        provider = response.headers.get(
                       "x-litellm-model-id", "unknown"),
        model    = choice.get("model", "unknown"),
    )

analyze.sh — đọc response headers

_call_backend() {
  http_status="$(curl --silent \
    --request POST \
    --header "Content-Type: application/json" \
    --data "${request_body}" \
    --output "${response_file}" \
    --dump-header "${response_headers}" \
    --write-out "%{http_code}" \
    --max-time ${CURL_TIMEOUT_SECONDS} \
    "${backend_url}/api/analyze-log")"

  if [[ "${http_status}" == "200" ]]; then
    AI_STATUS="ok"
    AI_ANALYSIS="$(cat "${response_file}")"
    # Read provider from custom response headers
    AI_PROVIDER="$(grep -i 'X-AI-Provider:' \
        "${response_headers}" | cut -d: -f2-)"
    AI_MODEL="$(grep -i 'X-AI-Model:' \
        "${response_headers}" | cut -d: -f2-)"
  fi
}

Log Preprocessing

3.000 dòng → 30 dòng. Tiết kiệm 96% token và tăng chất lượng phân tích.

AI Gateway

LiteLLM = 1 endpoint, nhiều provider. Fallback tự động. Không vendor lock-in.

RAG Memory

PostgreSQL + pgvector lưu lịch sử lỗi. AI học từ kinh nghiệm của team.

Security-first

Preprocess loại bỏ secrets trước khi gửi AI. Ollama hoàn toàn offline.
